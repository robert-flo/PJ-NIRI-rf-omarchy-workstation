## 2. Arquitectura Canónica de Worktrees (`ravn-git-bare-clone` v0.2.1)

Para evitar conflictos cuando varios agentes (`MonoCode`, `T3 Code`, `herdr`, `pj-trio`) editan el mismo repositorio en paralelo, el estándar obligatorio de la estación es **Bare Repo + Worktrees** (ADR 0019 de pj-template; fleet ADR 0011: **nunca `git worktree add` a mano**).

### Rutas por Defecto
- **Esquema global (estación):**
  - `BARE_HOME`: `/z/bare/<repo>.git`
  - `WORKTREES_HOME`: `/z/repos/<repo>/`
- **Esquema Home Repo (detección automática desde v0.2.1):**
  - Si se ejecuta dentro de un Home Repo (`HR-*`), `ravn-git-bare-clone` crea los bare en `.bares/<repo>.git` y los worktrees en `repos/<repo>/`.

### Herramientas del Ecosistema
- **CLI principal:** `ravn-git-bare-clone` / alias `ravn-wt` (paquete Arch `ravn-git-bare-clone` v0.2.1 en `[omarchy-personal]`).
- **Binarios globales incluidos en `/usr/bin/`:**
  - `ravn-git-bare-clone` / `ravn-wt` / `git-bare-clone`
  - `git-create-worktree`
  - `git-issue-worktree`

### Flujo Canónico de Trabajo con Worktrees
```bash
# 1. Clonar un repositorio en arquitectura bare + worktrees (idempotente)
ravn-git-bare-clone clone git@github.com:robert-flo/<repo>.git

# 2. Crear un worktree dedicado para una tarea o issue
git-issue-worktree -r /z/repos/<repo> -B <base> <numero-issue> <slug>

# 3. O crear un worktree con nombre libre
git-create-worktree -r /z/repos/<repo> -B <base> -b issue/<n>-<slug> -p '' <n>-<slug>

# 4. Al terminar el trabajo y tras el merge: remover el worktree de forma limpia
git -C /z/repos/<repo> worktree remove <ruta-worktree>
```

## 3. Auditoría Global de Flota con `forkhub`

Para garantizar que **ningún repositorio quede sucio o con commits sin `push`** en ninguna parte del disco, `forkhub` incorpora el comando `audit`:

```bash
# Auditar toda la flota canónica (/z/repos, /z/vaults, /z/pj-omarchy, /z/rf-dotfiles, /z/nvims, /z-drive/tries, /opt/src, /zt)
forkhub audit

# Mostrar únicamente repositorios con cambios sin commit, commits sin push o fuera de topología (/zt)
forkhub audit --dirty-only
```

- **Qué valida `forkhub audit`:**
  1. Cambios locales sin commitear o archivos sin seguimiento (`DIRTY`).
  2. Commits locales no enviados al remoto (`AHEAD` / `NO UPSTREAM`).
  3. Presencia de clones en zonas no canónicas como `/zt/` (`FUERA DE TOPOLOGÍA`).

## 4. GitHub Workflows (Estándar de Ramas, PRs y Merge Gate)

1. **Ramas protegidas:**
   - Repositorios propios (`PJ-NIRI-rf-omarchy-workstation`, `rf-dotfiles`): rama por defecto `master` (nunca `main`).
   - Forks (`PJ-NIRI-fo-*`, `omarchy`, `quickshell`, `nyxuri`): rama de trabajo `personal`.
   - **Prohibido** hacer commit directo a `master` o a upstreams externos (`StatIndet` no acepta PRs hechos con IA).
2. **Ciclo canónico de cambio (en worktree dedicado):**
   - Todo trabajo se orquesta con un Issue en `HR-CLAVIS` y sub-issues en el repo destino.
   - El WK o el OS programa exclusivamente en su worktree aislado `/z/repos/<repo>/<n>-<slug>`.
   - Ejecución de pruebas reales según `onboarding.yml` §como_probar y paso obligatorio de `/code-review`.
   - Apertura de PR con la skill `pr` conteniendo obligatoriamente:
     - `## Summary`
     - `## Evidence`
     - `## Merge Danger` (`Door: two-way|one-way`, `Blast Radius: Low|Medium|High`)
3. **Merge Gate Canónico:**
   - Si `Door: two-way` Y `Blast Radius: Low` -> auto-merge con squash y `--match-head-commit <sha>`.
   - Si `Door: one-way` o `Blast Radius != Low` -> escala a Roberto (`needs-roberto`).
4. **Commits sin atribución automática de agentes:**
   - Prohibido incluir trailers `Co-authored-by` o firmas de agentes en commits de todo el ecosistema.

## 5. Repositorios de Empaquetado Arch (`*-arch`) y Sincronización de Secretos

Para herramientas del ecosistema (`ravn-trio`, `ravn-git-bare-clone`, `ravn-sessionizer`), el empaquetado para el canal `[omarchy-personal]` se gestiona en repositorios dedicados con sufijo `-arch` (`ravn-trio-arch`, `ravn-git-bare-clone-arch`, `ravn-sessionizer-arch`).

### Sincronización Desatendida de Secretos en GitHub Actions
Los repositorios `*-arch` requieren dos secretos en GitHub Actions para compilar, firmar con GPG y publicar en `omarchy-personal-repo`:
1. `GPG_PRIVATE_KEY`: clave privada GPG para firmar los paquetes y la base de datos `omarchy-personal.db.tar.zst`.
2. `REPO_DEPLOY_KEY`: deploy key SSH con permisos de escritura hacia `robert-flo/omarchy-personal-repo`.

Para sincronizar estos secretos en nuevos repositorios de empaquetado de forma 100% desatendida y sin romper el flujo de trabajo:
- **Herramienta canónica:** `PJ-NIRI-rf-omarchy-workstation/scripts/secrets/sync-arch-package-secrets.sh`.
- **Runbook paso a paso:** [`pj-template/docs/runbook-secrets-empaquetado-arch.md`](https://github.com/robert-flo/pj-template/blob/main/docs/runbook-secrets-empaquetado-arch.md).
- **Regla de releases:** Todo cambio en un paquete debe documentarse en su respectivo `CAMBIOS.md` antes de generar el tag y release en GitHub.
