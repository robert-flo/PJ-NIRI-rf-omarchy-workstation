## 2. Arquitectura Canónica de Worktrees (`ravn-git-bare-clone`)

Para evitar conflictos cuando varios agentes (`MonoCode`, `T3 Code`, `herdr`, `Claude Code`, `Codex`) editan el mismo repositorio en paralelo, el estándar de la estación es **Bare Repo + Worktrees**:

### Rutas por Defecto (ya configuradas en `/opt/ravn-git-bare-clone`)
- **`BARE_HOME`:** `/z/bare/<repo>.git`
- **`WORKTREES_HOME`:** `/z/repos/<repo>/`

### Herramientas del Ecosistema
- **CLI principal:** `ravn-git-bare-clone` (paquete `ravn-git-bare-clone` en `[omarchy-personal]`, empaquetado desde [robert-flo/ravn-git-bare-clone-arch](https://github.com/robert-flo/ravn-git-bare-clone-arch) / [robert-flo/ravn-git-bare-clone](https://github.com/robert-flo/ravn-git-bare-clone)).
- **Binarios globales incluidos en `/usr/bin/`:**
  - `ravn-git-bare-clone` / `git-bare-clone`
  - `git-create-worktree`
  - `git-issue-worktree`
- **Experimentos rápidos:** `try-clone` ([robert-flo/try-clone](https://github.com/robert-flo/try-clone)) sobre `~/Work/tries` (`/z-drive/tries`).

### Flujo Estándar de Trabajo con Worktrees
```bash
# 1. Clonar un proyecto en arquitectura bare + worktrees
ravn-git-bare-clone clone git@github.com:robert-flo/<repo>.git
# -> Objetos bare en /z/bare/<repo>.git
# -> Worktrees en /z/repos/<repo>/

# 2. Crear un worktree dedicado para una tarea o sesión de agente
git-create-worktree <nombre-rama>

# 3. O crear un worktree vinculado directamente a un Issue de GitHub
git-issue-worktree <numero-issue>

# 4. Sincronizar ramas remotas faltantes como worktrees
ravn-git-bare-clone sync
```

> [!TIP]
> **Por qué esto resuelve la dispersión:** tanto `niri`, `niri-classic` como `omarchy` (`rollo`) ven exactamente `/z/repos/<repo>/<rama>` y `~/Work/tries` (`/z-drive/tries`) con los mismos permisos compartidos (`wheel` + ACLs de `/z`). Si cambias de usuario o entras por SSH desde el teléfono, el worktree está en el mismo path absoluto.

## 3. Auditoría Global de Flota con `forkhub`

Para garantizar que **ningún repositorio quede sucio o con commits sin `push`** en ninguna parte del disco, `forkhub` incorpora el comando `audit`:

```bash
# Auditar toda la flota canónica (/z/repos, /z/vaults, /z/pj-omarchy, /z/rf-dotfiles, /z/nvims, /z-drive/tries, /opt/src, /zt)
forkhub audit

# Mostrar únicamente repositorios con cambios sin commit, commits sin push o fuera de topología (/zt)
forkhub audit --dirty-only
```

- **Qué valida `forkhub audit`:**
  1. Cambios locales sin commitear o archivos sin seguimiento (`DIRTY`).
  2. Commits locales no enviados al remoto (`AHEAD` / `NO UPSTREAM`).
  3. Presencia de clones en zonas no canónicas como `/zt/` (`FUERA DE TOPOLOGÍA`).
- **Para forks de sistema (`/opt/src` y `/z/pj-omarchy`):** sigue vigente `forkhub status`, `forkhub upstream` y `forkhub sync-upstream`.

## 4. GitHub Workflows (Estándar de Ramas y PRs)

1. **Ramas protegidas:**
   - Repositorios propios (`PJ-NIRI-rf-omarchy-workstation`, `rf-dotfiles`): rama por defecto `master` (nunca `main`).
   - Forks (`PJ-NIRI-fo-*`, `omarchy`, `quickshell`, `nyxuri`): rama de trabajo `personal`.
   - **Prohibido** hacer commit directo a `master` o a upstreams externos (`StatIndet` no acepta PRs hechos con IA).
2. **Ciclo canónico de cambio (en worktree dedicado):**
   ```bash
   # En /z/repos/<repo>/<rama-feature> (o worktree de MonoCode / T3 Code)
   git status
   git push -u origin <rama-feature>
   gh pr create --base master --fill
   # Tras revisión: rebase sobre master más reciente -> merge -> borrar rama local y remota
   ```
3. **Commits sin atribución automática de agentes:**
   - No incluir trailers `Co-authored-by` en commits de este ecosistema.
