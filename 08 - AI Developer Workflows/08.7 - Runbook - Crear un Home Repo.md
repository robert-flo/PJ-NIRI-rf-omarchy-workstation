## 1. Qué es un Home Repo y qué NO es

Un **Home Repo** (o **proyecto padre**), según el [Home Repo Pattern de aihero](https://www.aihero.dev/the-home-repo-pattern), es un único repo que guarda las skills, el `AGENTS.md` y la documentación compartida de un proyecto que abarca varios repos. Los agentes se arrancan **ahí**, no dentro de un repo suelto, y el `AGENTS.md` apunta a los demás repos (en nuestro caso se clonan **adentro** y quedan ignorados por git).

En esta estación eso se concreta así:

- Un Home Repo es un **hijo de `robert-flo/pj-template` en modo dependencia**. "Hijo" significa **cliente del template**, no subproyecto.
- Tiene su propio trío **PM/WK/RV-`<HR>`** para **agy** (Antigravity) y **Cursor** (IDE y `cursor-agent`). El PM es el **único punto de entrada**: Roberto habla solo con él y él opera sobre todos los repos de `repos:` en `proyecto.yml`.
- El trío nace **genérico**: `repos: []`. Los repos que supervisa se le dicen en el **onboarding** (paso 13).

> [!CAUTION]
> **Grok Bot es una isla aparte.** El trío de Grok Bot (cloud agents) **no** sale de este runbook: se crea pidiéndole al CEO de Grok Bot "creá el trío para X", y sus fichas viven en `robert-flo/fleet`. pj-template solo cubre agy y Cursor (trabajo **local**). Que los dos tríos se llamen igual (`PM-HR-X`) está bien: es el mismo proyecto en dos mundos. El **único puente es GitHub** (issues y PRs). Regla: **un issue lo trabaja un solo mundo** (cloud o local), nunca los dos a la vez. **No** agregues adaptadores de Grok Bot (`.agents/grokbot.md`) ni menciones a Grok Bot / `robert-flo/fleet` en los archivos versionados del Home Repo (ver [[#8. Errores conocidos\|Errores conocidos]]). `./pj check` rechaza `.agents/grokbot.md` solo si no está en `extras:`; pj-omarchy lo versiona ahí, y ese es un extra suyo, no del molde.

### Qué versiona el Home Repo y qué no

| Versionado (a mano, por PR) | Generado por `./pj` (**nunca** se commitea) |
|---|---|
| `proyecto.yml`, `AGENTS.md`, `README.md`, `.gitignore`, `./pj`, `.github/workflows/pj-template.yml` (los **6** del modo dependencia) | `.pj/` (template al SHA de `template_ref` + `.pj/venv`) |
| `.trio/.gitkeep` y `.trio/README.md` (handoffs de `pj-trio`) | `.agents/` (reglas, skills, fichas `PM/WK/RV-<HR>.md` para agy, `generados.txt`) |
| **Extras** listados en `extras:` de `proyecto.yml`: `CLAUDE.md`, `<HR>.code-workspace`, `docs/agents/*.md` | `.cursor/` (`rules/pm-<hr>.mdc` con `alwaysApply`, `rules/no-cursor-coauthor.mdc`, `agents/wk-<hr>.md`, `agents/rv-<hr>.md`; `<hr>` = nombre en minúsculas) |
|  | Bloque `# >>> <HR>: repos (generado) >>>` de `.gitignore` y los clones de `repos:` |

**Por qué no se versiona lo generado:** las fichas citan reglas y skills que tampoco estarían al clonar; `./pj` deja todo en disco igual byte a byte desde un SHA fijo, el diff de cada PR es solo lo que escribió Roberto y actualizar el template es cambiar una línea (`template_ref`).

## 3. Reglas que no se negocian

- **Ningún commit, en ningún repo, lleva trailer ni firma de agente**: nada de `Co-authored-by:`, nada de `agente: … · plataforma: …`. Si el entorno los inyecta, usá `git commit-tree` (ver [[#Paso 9 — Commit, push y PR al Home Repo\|paso 9]]).
- Identidad de git: `Roberto Flores <25asab015@ujmd.edu.sv>`.
- Rama por defecto de los repos propios: **`master`, nunca `main`** (`rama_base: "master"`).
- **Nunca commit directo a `master`**: rama auxiliar → PR → RV responde `APRUEBO <sha>` sobre el head exacto → el PM mergea con squash, `--delete-branch` y `--match-head-commit`, **sin esperar orden de Roberto** ([ADR 0014](https://github.com/robert-flo/pj-template/blob/main/docs/adr/0014-el-pm-mergea-tras-apruebo.md)). Si la cabeza del PR cambió después del `APRUEBO`, no se mergea: otra revisión.
- `git pull --rebase --autostash` antes de trabajar y antes de empujar. **Nunca `--force`.**
- Nunca PRs a upstreams (omacom/omarchy, StatIndet, etc.).
- Secretos: **nunca** en texto plano, ni en el chat, ni en un archivo, ni en la salida de un comando.
- Temporales en la PC: `~/.cache/ravn-piloto/`.

## 5. Runbook principal (camino manual)

### Paso 0 — Variables y prerrequisitos

**Qué:** fijar el nombre y comprobar herramientas. **Por qué:** todos los comandos de abajo usan estas variables; un `gh` sin sesión o sin `wheel` rompe pasos más adelante.

```bash
export HR="HR-EJEMPLO"                       # nombre exacto del repo y del trío (PM-$HR, WK-$HR, RV-$HR)
export AREA="home repo de EJEMPLO — punto único de entrada del trío a todos sus repos"
export DEST="/z-home-repos/$HR"
export TPL="$HOME/.cache/ravn-piloto/pj-template"
mkdir -p "$HOME/.cache/ravn-piloto"

gh auth status                               # debe decir: Logged in to github.com account robert-flo
id -nG | tr ' ' '\n' | grep -qx wheel && echo "wheel OK"
test -d /z-home-repos && stat -c '%a %G' /z-home-repos   # esperado: 2770 wheel
command -v python3 git make gh agy cursor-agent
```

**Verificación:** `gh` logueado como `robert-flo`, `wheel OK`, `/z-home-repos` en `2770 wheel`. `HR` cumple `^[A-Za-z0-9][A-Za-z0-9._-]*$` (lo exige el esquema). `agy`/`cursor-agent` pueden faltar en la máquina de preparación; solo hacen falta en el paso 12.

### Paso 1 — Repo en GitHub con rama `master`

**Qué:** asegurar que `robert-flo/$HR` existe y su rama por defecto es `master`. **Por qué:** `rama_base` y todos los PRs apuntan a `master`; el repo necesita al menos un commit para poder abrir PRs contra él.

```bash
if gh repo view "robert-flo/$HR" >/dev/null 2>&1; then
  echo "ya existe robert-flo/$HR"
else
  gh repo create "robert-flo/$HR" --private --add-readme --description "Home repo de $HR (hijo de pj-template)"
fi
# Si GitHub lo creó con main, renombrar a master (no toca historia, no es --force):
[ "$(gh repo view "robert-flo/$HR" --json defaultBranchRef --jq .defaultBranchRef.name)" = main ] \
  && gh api -X POST "repos/robert-flo/$HR/branches/main/rename" -f new_name=master
gh repo view "robert-flo/$HR" --json defaultBranchRef --jq .defaultBranchRef.name   # -> master
```

**Verificación:** imprime `master`.

> [!NOTE]
> `--add-readme` crea el commit inicial **en GitHub**, así ningún agente commitea a mano en `master`. Privado es el default recomendado para el Home Repo; HR-CLAVIS es público y también funciona. pj-template ya es **público**, así que un hijo público o privado corre el sync en su propio workflow (ya no hace falta llamar workflows del template).

### Paso 2 — Clon canónico en `/z-home-repos` y rama auxiliar

**Qué:** clonar en su ruta canónica y trabajar en una rama. **Por qué:** [[08.3 - Topologia Canonica de Repositorios, Worktrees y GitHub Workflows\|08.3]] define `/z-home-repos/` como el hogar de los Home Repos (permisos compartidos para todos los usuarios); nada va directo a `master`.

```bash
[ -d "$DEST/.git" ] || gh repo clone "robert-flo/$HR" "$DEST"
cd "$DEST"
git config user.name "Roberto Flores"
git config user.email "25asab015@ujmd.edu.sv"
git fetch origin
git checkout master && git pull --rebase --autostash origin master
export SHA_ANTES=$(git rev-parse HEAD)   # para la verificación de trailers (solo commits nuevos)
RAMA="ceo/aplicar-pj-template"
# Retomar la rama si ya existe (local o remota). Nunca `checkout -B` desde master:
# eso la resetea, se pierde el commit del paso 9 y el .gitignore generado.
if git show-ref --verify --quiet "refs/heads/$RAMA"; then
  git checkout "$RAMA"
  if git show-ref --verify --quiet "refs/remotes/origin/$RAMA"; then
    git pull --rebase --autostash origin "$RAMA"
  fi
elif git show-ref --verify --quiet "refs/remotes/origin/$RAMA"; then
  git checkout -B "$RAMA" "origin/$RAMA"
else
  git checkout -B "$RAMA"
fi
```

**Verificación:** `git -C "$DEST" branch --show-current` → `ceo/aplicar-pj-template`; `git remote -v` apunta a `robert-flo/$HR`.

### Paso 3 — Traer pj-template y fijar `template_ref`

**Qué:** clonar/actualizar pj-template y leer el SHA completo de `main` **en este momento**. **Por qué:** `./pj` trae el template **exactamente** a ese SHA; los archivos fijos del hijo (`./pj`, workflow, `.gitignore`) se copian de ese mismo SHA, no de un valor hardcodeado. Si `main` avanzó entre corridas, el paso 5a actualiza `template_ref` de forma explícita para que no quede viejo.

```bash
[ -d "$TPL/.git" ] || gh repo clone robert-flo/pj-template "$TPL"
git -C "$TPL" checkout main && git -C "$TPL" pull --rebase --autostash
export SHA="$(gh api repos/robert-flo/pj-template/commits/main --jq .sha)"
[ "$SHA" = "$(git -C "$TPL" rev-parse HEAD)" ] && echo "template_ref = $SHA"
```

**Verificación:** imprime un SHA de 40 caracteres hex y coincide con el clon local.

### Paso 4 — Archivos fijos del hijo (`./pj`, workflow, `.gitignore`)

**Qué:** copiar los 3 archivos que manda pj-template, **del SHA de `template_ref`** (el `main` actual, paso 3). **Por qué:** no se editan en el hijo; el PR de sync diario los mantiene iguales al template (`./pj` avisa si difieren). Se copian con `git show $SHA:...` para no mezclar un `main` nuevo con un `template_ref` viejo.

```bash
cd "$DEST"
[ -n "$SHA" ] || { echo "falta SHA (paso 3)"; exit 1; }
git -C "$TPL" show "$SHA:plantillas/hijo/pj" > ./pj && chmod +x ./pj
mkdir -p .github/workflows
git -C "$TPL" show "$SHA:plantillas/hijo/pj-template.yml" > .github/workflows/pj-template.yml
[ -e .gitignore ] || git -C "$TPL" show "$SHA:plantillas/hijo/gitignore" > .gitignore
grep -qxF '/rf-*/' .gitignore || { printf '\n'; git -C "$TPL" show "$SHA:plantillas/hijo/gitignore"; } >> .gitignore
# El workspace se versiona aunque un gitignore global ignore *.code-workspace:
grep -qxF "!$HR.code-workspace" .gitignore || printf '\n# Workspace del proyecto aunque esté en un gitignore global\n!%s.code-workspace\n' "$HR" >> .gitignore
```

**Verificación:** `git -C "$TPL" show "$SHA:plantillas/hijo/pj" | cmp - ./pj` y `git -C "$TPL" show "$SHA:plantillas/hijo/pj-template.yml" | cmp - .github/workflows/pj-template.yml` sin salida; `.gitignore` contiene `/rf-*/`, `/fo-*/` y `!$HR.code-workspace`. **No** escribas a mano el bloque `# >>> $HR: repos (generado) >>>` ni las líneas `/.pj/`, `/.agents/`, `/.cursor/`: las escribe `./pj` en ese bloque (paso 7). La plantilla `plantillas/hijo/gitignore` no las trae.

### Paso 5 — Archivos a mano: `proyecto.yml`, `AGENTS.md`, `README.md`, `.trio/`, extras

**Qué:** escribir los datos del proyecto y la cabecera del template. **Por qué:** `proyecto.yml` es el único archivo de datos (lo valida `schema/proyecto.schema.json`: sin claves de más, textos entre comillas porque un `#` sin comillas corta el valor). `AGENTS.md` le dice a cualquier agente que corra `./pj` si no ve `.agents/reglas/`.

**5a. `proyecto.yml`** (solo se crea si no existe; si existe, se actualiza `template_ref` al SHA actual de `main`, de forma explícita, para que no quede viejo si el template avanzó entre corridas):

```bash
cd "$DEST"
[ -e proyecto.yml ] || cat > proyecto.yml <<YML
# Datos del proyecto. Es el único archivo de datos que llenás a mano; después: ./pj
# Lo valida schema/proyecto.schema.json de pj-template. Los textos van entre comillas (un # sin comillas corta el valor).
proyecto: "$HR"           # nombre del trío: PM-<proyecto>, WK-<proyecto>, RV-<proyecto>
area: "$AREA"
rama_base: "master"             # rama de los PR finales
template_ref: "$SHA"   # SHA de robert-flo/pj-template; lo sube el PR de sync
# Repos hijos. dir = carpeta local, ignorada en .gitignore. Se llenan en el onboarding del PM.
repos: []
#  - dir: "rf-ejemplo"
#    repo: "robert-flo/ejemplo"
#    rama: "master"
#    nota: "qué es este repo en una frase"
# Specs en curso: ref = dueño/repo#N, orden entero, exactamente uno con primero: true.
specs: []
notas: |
  Home repo (Home Repo Pattern de aihero) de $HR. El PM de acá es la única puerta de entrada y
  opera sobre todos los repos que se clonan adentro (repos:, vacío hasta el onboarding). Rama por
  defecto master (nunca main), nada directo a master: rama auxiliar o worktree, PR, rebase, merge y
  limpiar rama. Los commits van sin trailers Co-authored-by ni atribución a agentes.
# Archivos propios a mano que pj-template conserva sin tocar.
extras:
  - "CLAUDE.md"
  - "$HR.code-workspace"
# Skills extra por rol, además de plantillas/roles.yml de pj-template.
skills_extra: {}
YML
# template_ref siempre al SHA actual de main (también si el archivo ya existía):
sed -i -E "s|^template_ref:[[:space:]].*|template_ref: \"$SHA\"   # SHA de robert-flo/pj-template; lo sube el PR de sync|" proyecto.yml
grep -qE '^rama_base:[[:space:]]*"master"' proyecto.yml || echo "AVISO: rama_base no es master; revisá proyecto.yml" >&2
grep -nE '^(proyecto|rama_base|template_ref):' proyecto.yml
```

> [!WARNING]
> `notas` y `area` **no** pueden ser las del molde (`./pj` falla si quedan datos de pj-template). Completá `notas` con el contexto real del proyecto si Roberto lo dio; si no, el texto de arriba es válido.

**5b. `AGENTS.md`** — cabecera del template arriba y, si el repo ya tenía `AGENTS.md`, sus reglas propias debajo **intactas**:

```bash
cd "$DEST"
if ! grep -q 'corré `./pj` antes de nada' AGENTS.md 2>/dev/null; then
  { cat <<MD

- Extras conservados a mano (\`extras:\` de \`proyecto.yml\`).
- \`.trio/\`: handoffs de \`pj-trio\` (\`.trio/<ticket>/\`), se commitean.
- Regla de merge: el PM mergea tras el \`APRUEBO <sha>\` del RV sobre el head exacto, con \`gh pr merge <N> --squash --delete-branch --match-head-commit <sha>\`, sin esperar orden de Roberto (ADR 0014). Si la cabeza cambió, pide otra revisión y no mergea.
- Los commits van sin trailers ni atribución a agentes.
```

**5c. `README.md`, `CLAUDE.md`, workspace y `.trio/`** (`CLAUDE.md`, workspace y `.trio/` solo si faltan; `README.md` de un repo existente no se pisa: se conserva título y descripción, como HR-CLAVIS#2 con `README.md:3`, y solo se le suma el bloque de comandos):

```bash
cd "$DEST"
if ! grep -q '^./pj listo' README.md 2>/dev/null; then
  bloq=$(cat <<MD

./pj check      # esquema de proyecto.yml, idempotencia y prueba de humo
./pj clonar     # clona los repos de proyecto.yml adentro
./pj agy        # una vez por máquina y usuario; después: agy --agent PM-$HR
./pj humo       # prueba de humo; con agy instalado arranca PM-$HR sin interacción
\`\`\`

Necesitás \`python3\`, \`gh\`, \`git\` y \`make\` (\`./pj\` arma su propio \`.pj/venv\`). Reglas y mapa de repos: \`AGENTS.md\`.

)
  if [ -e README.md ]; then
    { cat README.md; printf '\n%s\n' "$bloq"; } > README.md.nuevo && mv README.md.nuevo README.md
  else
    cat > README.md <<MD

Home Repo y meta-repo del trío PM/WK/RV-$HR: el PM de acá es la única puerta de entrada a todos los repos del proyecto. Hijo de \`robert-flo/pj-template\` en modo dependencia.

  fi

[ -e "$HR.code-workspace" ] || printf '{\n\t"folders": [\n\t\t{\n\t\t\t"name": "0. Home Repo (%s)",\n\t\t\t"path": "."\n\t\t}\n\t],\n\t"settings": {}\n}\n' "$HR" > "$HR.code-workspace"

[ -e .trio/README.md ] || cat > .trio/README.md <<MD
# .trio/ — handoffs del trío PM/WK/RV en herdr

Cada ticket que corre el trío deja acá su carpeta \`.trio/<ticket>/\` (plan, reporte del WK, veredicto del RV), y se commitea a git.

\`\`\`

- \`<ticket>\`: número del issue a trabajar. \`<miembro>\`: el \`dir\` del repo en \`proyecto.yml\` donde cae el ticket.
- \`pj-trio\` es \`/usr/bin/pj-trio\` (paquete de \`robert-flo/ravn-trio\`). Abre en herdr las pestañas \`pm\`, \`wk\` y \`rv\` con \`agy --agent PM-$HR\` / \`WK-$HR\` / \`RV-$HR\`. El estado se ve con \`trio-status\`.
- El PM mergea tras el \`APRUEBO <sha>\` del RV sobre el head exacto, sin esperar orden de Roberto: \`gh pr merge <N> --squash --delete-branch --match-head-commit <sha>\`. Si la cabeza cambió, pide otra revisión y no mergea.
MD
# Nunca `git add -A` acá: .gitignore todavía no tiene el bloque generado (/.pj/, /.agents/, /.cursor/),
# que escribe ./pj en el paso 7. Un add ciego stagea esas carpetas y ./pj check falla.
for f in proyecto.yml AGENTS.md README.md .gitignore pj \
         .github/workflows/pj-template.yml \
         .trio/.gitkeep .trio/README.md \
         CLAUDE.md "$HR.code-workspace"; do
  [ -e "$f" ] && git add -- "$f"
done
```

**Verificación:** `git status --short` muestra solo `proyecto.yml`, `AGENTS.md`, `README.md`, `.gitignore`, `pj`, `.github/workflows/pj-template.yml`, `.trio/.gitkeep`, `.trio/README.md`, `CLAUDE.md` y `$HR.code-workspace`. `grep -niE 'grok ?bot|robert-flo/fleet' AGENTS.md README.md proyecto.yml` **sin salida**.

### Paso 6 — Secreto `PJ_TEMPLATE_TOKEN` (antes del PR)

**Qué:** cargar el PAT como secreto del repo. **Por qué:** pj-template ya es **público**, así que el job `check` puede bajar el template sin secreto. El secreto sigue haciendo falta para el job `sync`: los `actions/checkout` con `token:` y el PR de sync que dispara CI. Va **antes** del push para que el sync (04:17 El Salvador, o al dispararlo) tenga el token a la primera.

- Token: PAT **fine-grained** de `robert-flo`, con acceso a `robert-flo/pj-template` y al Home Repo (o a todos los hijos), permisos *Contents*, *Pull requests* y *Workflows* en **Read and write**. Es el mismo `PJ_TEMPLATE_TOKEN` de los otros hijos; si al PAT le falta el repo nuevo, Roberto lo agrega en GitHub → Settings → Developer settings → Fine-grained tokens.
- Lo carga **Roberto** (o el agente con un campo seguro, sin verlo nunca):

```bash
gh secret set PJ_TEMPLATE_TOKEN -R "robert-flo/$HR"   # lo pide por stdin oculto; nunca va en la línea de comando
gh secret list -R "robert-flo/$HR"                    # verificación: debe listar PJ_TEMPLATE_TOKEN (solo nombre y fecha)
```

> [!CAUTION]
> Nunca `echo $TOKEN`, nunca `--body "<token>"`, nunca un archivo con el token. Si el agente no tiene campo seguro, se detiene y le pide a Roberto que corra el primer comando.

### Paso 7 — Generar el trío y pasar `./pj check`

**Qué:** `./pj` trae el template al SHA, genera `.agents/` y `.cursor/` y escribe el bloque generado de `.gitignore`. **Por qué:** `./pj check` valida esquema, idempotencia, que no haya archivos generados versionados, que los extras estén versionados, y la prueba de humo estática de PM/WK/RV.

```bash
cd "$DEST"
./pj
# ./pj ya escribió el bloque generado de .gitignore (/.pj/, /.agents/, /.cursor/ y /.pj-sync/).
# `git add -A` es seguro a partir de acá.
git add -A && ./pj check
ls .agents/agents/            # PM-$HR.md  RV-$HR.md  WK-$HR.md
ls .cursor/rules .cursor/agents   # pm-<hr>.mdc, no-cursor-coauthor.mdc / rv-<hr>.md, wk-<hr>.md (minúsculas)
grep -E '^/\.(pj|agents|cursor)/$' .gitignore   # las tres líneas del bloque generado
```

**Verificación:** `./pj check` termina con `check: todo bien` (ninguna línea `FALLA`); existen `.agents/agents/{PM,WK,RV}-$HR.md`, `.cursor/rules/pm-<hr>.mdc` y `.cursor/agents/{wk,rv}-<hr>.md` (`<hr>` = `$HR` en minúsculas, p. ej. `pm-hr-clavis.mdc`); `git status --short` **no** lista nada bajo `.pj/`, `.agents/` ni `.cursor/`; `.gitignore` contiene `/.pj/`, `/.agents/` y `/.cursor/` dentro del bloque `# >>> $HR: repos (generado) >>>`.

### Paso 8 — Skills de ingeniería (`setup-matt-pocock-skills`) y etiquetas

**Qué:** configurar tracker, etiquetas y docs de dominio para las skills. **Por qué:** `to-spec`, `to-tickets`, `triage`, etc. leen `docs/agents/*.md` y usan las etiquetas; sin esto el PM no sabe dónde abrir issues.

1. El agente lee y ejecuta `.agents/skills/setup-matt-pocock-skills/SKILL.md` (la copia de `robert-flo/skills@personal` que trajo `./pj`; **nunca** la de upstream). Respuestas fijas para un Home Repo:
   - **Issue tracker:** GitHub Issues de `robert-flo/$HR` (CLI `gh`), "PRs as a request surface" apagado.
   - **Triage labels:** las por defecto (`needs-triage`, `needs-info`, `ready-for-agent`, `ready-to-merge` como rol *ready-for-human*, `wontfix`).
   - **Domain docs:** single-context (`GLOSSARY.md` y `docs/adr/` en la raíz, se crean cuando hagan falta).
   - Resultado: `docs/agents/issue-tracker.md`, `docs/agents/triage-labels.md`, `docs/agents/domain.md` y una sección `## Agent skills` en `AGENTS.md` (no en `CLAUDE.md`, que solo importa `AGENTS.md`).
2. Sumar esos archivos a `extras:` y volver a validar:

```bash
cd "$DEST"
# `sed a` inserta después de la línea del workspace; el bucle va al revés para que
# extras: quede issue-tracker, triage-labels, domain (como en HR-CLAVIS).
for f in docs/agents/domain.md docs/agents/triage-labels.md docs/agents/issue-tracker.md; do
  grep -qF "\"$f\"" proyecto.yml || sed -i "/^  - \"$HR.code-workspace\"$/a\\  - \"$f\"" proyecto.yml
done
git add -A && ./pj check
```

3. Etiquetas (idempotente, `gh label create --force`) desde el template al SHA fijado:

```bash
bash "$DEST/.pj/tpl/scripts/etiquetas.sh" "robert-flo/$HR"
gh label list -R "robert-flo/$HR" --json name --jq '.[].name'
```

**Verificación:** `./pj check` en verde; las etiquetas `needs-triage`, `needs-info`, `ready-for-agent`, `ready-to-merge`, `wontfix` y `spec` aparecen en la lista.

### Paso 9 — Commit, push y PR al Home Repo

**Qué:** un commit limpio en la rama auxiliar y PR a `master`. **Por qué:** nada entra a `master` sin PR y revisión.

```bash
cd "$DEST"
git add -A
git diff --cached --quiet || git commit -m "feat(home-repo): aplicar pj-template a $HR" \
  -m "$HR pasa a ser home repo hijo de robert-flo/pj-template en modo dependencia (template_ref ${SHA:0:7}, rama_base master, repos y specs vacíos hasta el onboarding del PM). ./pj genera PM/WK/RV-$HR para agy y Cursor; docs/agents/ de setup-matt-pocock-skills."
# Verificar que no se coló ningún trailer:
git log -1 --format=%B | grep -niE 'co-authored-by|^agente:|plataforma:' && echo "HAY TRAILER: rehacer con commit-tree" || echo "sin trailer"
git pull --rebase --autostash origin master
git push -u origin HEAD
gh pr view --json url --jq .url 2>/dev/null || gh pr create -R "robert-flo/$HR" --base master \
  --title "feat(home-repo): aplicar pj-template a $HR" \
  --body "Aplica robert-flo/pj-template (modo dependencia) a $HR siguiendo el runbook 08.7 del vault workstation. Versiona solo los archivos a mano; .pj/, .agents/ y .cursor/ los genera ./pj. repos: vacío hasta el onboarding."
```

Si el entorno inyecta trailers, rehacé el commit así (sin `--force`: la rama aún no tiene el commit malo en el remoto; si ya lo tiene, sumá un commit nuevo en vez de reescribir):

```bash
git reset --soft HEAD~1
sha=$(git commit-tree "$(git write-tree)" -p HEAD -m "feat(home-repo): aplicar pj-template a $HR")
git update-ref "refs/heads/$(git branch --show-current)" "$sha"
```

**Verificación:** el PR existe contra `master`; `gh pr checks` → el job `check` del workflow `pj-template` en verde.

### Paso 10 — Registrar el hijo en `family.yml` de pj-template

**Qué:** sumar `robert-flo/$HR` a `hijos:`. **Por qué:** `notify-children.yml` avisa a los hijos de `family.yml` cuando cambia el template, y `vigilar-hijos.yml` abre un issue si hay hijos sin registrar o sin secreto.

```bash
cd "$TPL"
git config user.name "Roberto Flores"
git config user.email "25asab015@ujmd.edu.sv"
git checkout main && git pull --rebase --autostash
if grep -qx "  - robert-flo/$HR" family.yml; then echo "ya registrado"
elif url=$(gh pr list -R robert-flo/pj-template --head "family/$HR" --state open --json url --jq '.[0].url') && [ -n "$url" ]; then echo "ya hay PR: $url"
else
  git fetch origin
  if git show-ref --verify --quiet "refs/remotes/origin/family/$HR"; then
    git checkout -B "family/$HR" "origin/family/$HR"
    # Si un PR anterior se cerró sin mergear y main avanzó, no se hace --force:
    # se abre una rama nueva desde main.
    if ! git merge-base --is-ancestor main HEAD; then
      git checkout -B "family/$HR-$(date +%Y%m%d)" main
    fi
  else
    git checkout -B "family/$HR"
  fi
  grep -qx "  - robert-flo/$HR" family.yml || printf '  - robert-flo/%s\n' "$HR" >> family.yml
  git add family.yml
  git diff --cached --quiet || git commit -m "chore(family): agregar $HR a los hijos"
  rama=$(git branch --show-current)
  git push -u origin "$rama"
  gh pr create -R robert-flo/pj-template --base main --head "$rama" \
    --title "chore(family): agregar $HR a los hijos" --body "Home repo $HR aplicado por PR en robert-flo/$HR (runbook 08.7)."
fi
```

**Verificación:** PR abierto en pj-template con un diff de **una línea**; commit sin trailer. pj-template usa `main` (es la excepción histórica: es el template).

### Paso 11 — Revisión del RV y merge (el PM mergea tras el APRUEBO)

**Qué:** RV-`$HR` (o el RV que Roberto indique) revisa ambos PRs. **Por qué:** nada se mergea sin `APRUEBO <sha>` sobre el head exacto. En un Home Repo el PM mergea ahí mismo, **sin esperar orden de Roberto** ([ADR 0014](https://github.com/robert-flo/pj-template/blob/main/docs/adr/0014-el-pm-mergea-tras-apruebo.md), `pm.md` paso 8, `comun.md`).

1. RV revisa y responde `APRUEBO <sha>` o `BLOQUEO` con fixes. Si hay fixes: nuevo commit en la misma rama, `pull --rebase --autostash`, push (sin `--force`), re-revisión. Volvé a correr este runbook desde el principio: los pasos ya hechos no cambian nada (la rama auxiliar se retoma, no se resetea a `master`).
2. Con `APRUEBO <sha>` sobre el head exacto: etiqueta `ready-to-merge` en el PR. El PM mergea (primero el Home Repo, después `family.yml`). Si la cabeza del PR cambió después del `APRUEBO`, no se mergea: otra revisión.

```bash
N_HR="NUMERO";  APRUEBO_HR="SHA_APROBADO"    # PR en robert-flo/$HR y SHA exacto del APRUEBO del RV
N_TPL="NUMERO"; APRUEBO_TPL="SHA_APROBADO"   # PR de family.yml en pj-template y su SHA aprobado
gh pr merge "$N_HR" -R "robert-flo/$HR" --squash --delete-branch --match-head-commit "$APRUEBO_HR"
gh pr merge "$N_TPL" -R robert-flo/pj-template --squash --delete-branch --match-head-commit "$APRUEBO_TPL"
```

**Verificación:** ambos PRs `MERGED`; las ramas auxiliares no existen en el remoto (`git ls-remote --heads origin`).

### Paso 12 — Dejar el Home Repo listo en la PC y arrancar el PM

**Qué:** volver a `master`, limpiar la rama local y correr el paso único post-clone. **Por qué:** `./pj listo` hace pull, trae el template, genera, instala hooks `post-merge`/`post-checkout` (cada `git pull` regenera solo), enlaza las fichas en agy, clona `repos:` y corre `check`.

```bash
cd "$DEST"
git checkout master && git pull --rebase --autostash
git branch -D ceo/aplicar-pj-template 2>/dev/null || true
./pj listo
```

En **cada usuario** que vaya a usar agy (`niri`, `omarchy`, etc.), una vez: `cd /z-home-repos/$HR && ./pj agy` (enlaza en **su** `~/.gemini/config/agents`).

Arrancar:

```bash
cd "/z-home-repos/$HR" && agy --agent "PM-$HR"     # agy (o ./pj listo --abrir)
cursor "/z-home-repos/$HR/$HR.code-workspace"       # Cursor IDE: el PM es la regla alwaysApply
cd "/z-home-repos/$HR" && cursor-agent              # Cursor CLI: lee AGENTS.md y .cursor/
```

**Verificación:** `./pj listo` termina con `pj: listo. Para arrancar:  agy --agent PM-$HR`; `./pj humo` con agy instalado hace que el PM responda con su nombre.

### Paso 13 — Onboarding: decirle al PM qué repos supervisa

**Qué:** Roberto le dice al PM "supervisás X, Y, Z". **Por qué:** el trío nace genérico; los repos entran a `repos:` por PR y `./pj clonar` los trae **adentro** del Home Repo (ignorados por git, bloque generado de `.gitignore`).

El PM, en una rama auxiliar del Home Repo:


Además actualiza la tabla **Arquitectura** de `AGENTS.md`. Luego `./pj check`, PR, RV, y el PM mergea tras el `APRUEBO <sha>` (sin esperar orden de Roberto). En la PC:

```bash
cd "/z-home-repos/$HR" && git pull --rebase --autostash && ./pj clonar
```

**Verificación:** cada `dir` existe con su rama (`OK: <dir> en <rama>`) y `git status` del Home Repo sigue limpio.

## 8. Errores conocidos

| Síntoma | Causa | Solución |
|---|---|---|
| `make nuevo-hijo P=HR-X` crea `robert-flo/pj-HR-X` | `nuevo-hijo.sh` fuerza el prefijo `pj-` y siempre crea repo nuevo | Para `HR-*` usar el camino manual (pasos 0–14). |
| `nuevo-hijo` deja `rama_base: "main"` y commitea directo | Hace `git init -b main` y commit/push directo a la rama por defecto | No usarlo para repos propios con `master`; si se usó, corregir por PR. |
| Commits viejos con `agente: … · plataforma: …` | Regla anterior a [pj-template#33](https://github.com/robert-flo/pj-template/pull/33) (ya **mergeado** en `515e282`) | No reescribir historia (pediría `--force`). Los commits nuevos no llevan trailer (`comun.md`). |
| `./pj check`: "archivos versionados que deberían venir de pj-template: CLAUDE.md …" | Un archivo propio versionado que no está en `extras:` | Agregarlo a `extras:` en `proyecto.yml`. |
| `./pj check`: "extras: X no está versionado" | Se listó en `extras:` pero no se hizo `git add` | `git add -A` antes de `./pj check` (paso 7). |
| `./pj check`: "… es generado y no debe versionarse" | Se commiteó algo de `.pj/`, `.agents/` o `.cursor/` | `git rm -r --cached .agents .cursor .pj` y volver a correr `./pj`. |
| `./pj check` rechaza referencias a `grok bot` / `robert-flo/fleet` | El check busca otras plataformas en lo versionado (fuera de extras) | Sacar esas menciones; Grok Bot es una isla, el puente es GitHub. |
| `./pj` falla por "datos del molde" | `proyecto: pj-template`, notas del molde o falta `template_ref` | Completar `proyecto.yml` (paso 5a). |
| `./pj` falla con un valor cortado | `#` sin comillas en `area`, `titulo`, `nota` o `ref` | Poner todos los textos entre comillas. |
| No hay PRs de sync / el job `sync` falla | Falta `PJ_TEMPLATE_TOKEN` o el PAT no incluye el repo (el job `check` ya no lo necesita para bajar el template, que es público; el `sync` sí, para `actions/checkout` con `token:` y para abrir el PR) | Paso 6; revisar que el PAT tenga acceso al repo nuevo. |
| `agy --agent PM-HR-X` arranca un agente sin herramientas | Las fichas no están enlazadas en `~/.gemini/config/agents` de ese usuario | `./pj agy` en ese usuario. |
| El `.code-workspace` no aparece en `git status` | Gitignore global ignora `*.code-workspace` | Línea `!<HR>.code-workspace` en `.gitignore` (paso 4). |
| `.trio/README.md` copiado de otro hijo apunta a `scripts/pj-trio` del vault | `pj-trio` se movió a `robert-flo/ravn-trio` (`/usr/bin/pj-trio`) | Usar el texto del paso 5c. |
| Se buscan `robert-flo/antigravity-fleet` o `pj-antigravity` | Borrados; los reemplazó pj-template | No usarlos. Respaldo de antigravity-fleet: `pj-template/docs/adr-antigravity/`. |

## 9. Camino alternativo — `make nuevo-hijo`

Solo para un meta-repo **nuevo** con nombre `pj-<x>` y aceptando sus limitaciones (prefijo `pj-`, rama `main`, commit directo a esa rama):

```bash
cd "$TPL" && git pull --rebase --autostash
read -rs PJ_TEMPLATE_TOKEN && export PJ_TEMPLATE_TOKEN    # se pega sin eco; nunca se imprime
make nuevo-hijo P=<x>                    # crea robert-flo/pj-<x> en /z-drive/tries/rf-pj-<x>
# No uses DIR=/z-home-repos: el script clona en <DIR>/rf-pj-<x>, y 08.3 pide /z-home-repos/<nombre>.
# Para un Home Repo HR-* usá el camino manual (pasos 0–14), que clona en /z-home-repos/$HR.
unset PJ_TEMPLATE_TOKEN
```

Hace: crea `robert-flo/pj-<x>` privado si no existe, lo clona (por defecto en `/z-drive/tries/rf-pj-<x>`; con `DIR=` en `<DIR>/rf-pj-<x>`), escribe los 6 archivos con `template_ref` = `main` actual, corre `./pj` y `./pj check`, commit y push, carga el secreto y abre el PR de `family.yml`. Es re-ejecutable: un hijo existente conserva sus archivos. Después siguen los pasos 2 (rama aux), 5 (completar `proyecto.yml`/`AGENTS.md`), 8, 11, 12 y 13 de este runbook.
